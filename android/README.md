# LogiFollow

키보드가 채널을 옮기면 마우스도 같이 옮긴다. 안드로이드(폰 / 삼성 덱스)용.
**USB Logi Bolt 리시버**와 **블루투스 직결(BLE++ 커스텀 GATT)**을 모두 지원한다 (v0.3).
프로토콜 근거는 상위 폴더의 `HANDOFF.md`.

## 무엇이 되고 무엇이 안 되는가

**된다 — USB 리시버 또는 블루투스 직결로 여기서 나갈 때.**
- USB Bolt 리시버가 꽂혀 있으면 **USB 리시버 모드**(`FollowEngine`)로 동작한다.
- USB 리시버가 없으면 자동으로 **블루투스 직결(BLE++) 모드**(`BleFollowEngine`)로 시작해,
  로지텍 커스텀 GATT 서비스(`00010000-0000-1000-8000-011F2000046D`)로 키보드의 `0x1814` 알림을 받아 마우스를 함께 전환한다.
  (표준 HID 서비스 `0x1812`가 아니라 커스텀 UUID이므로 안드로이드 `SecurityException`을 우회한다.)

**안 된다 — 덱스로 돌아올 때.**
마우스는 자기가 선택한 채널로만 수신한다. 마우스가 맥에 가 있으면 폰의
리시버는 마우스에게 말을 걸 방법이 없다. 프로토콜의 한계지 구현 문제가 아니다.
돌아올 때는 마우스 바닥 버튼을 눌러야 한다.

## 빌드

```
./build.sh
```

JDK 17 은 `/opt/homebrew/opt/openjdk@17`, SDK 는 `~/Library/Android/sdk`
에 있다고 가정한다 (2026-09-10 에 이 맥에 설치함). 없다면:

```
brew install openjdk@17
# cmdline-tools 를 ~/Library/Android/sdk/cmdline-tools/latest 에 풀고
sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-35" "build-tools;35.0.0"
```

## 설치와 사용

```
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

1. 리시버를 허브에 꽂는다. 등록해둔 VID/PID 라 앱이 바로 뜬다.
   권한 다이얼로그에서 **"이 USB 기기에 항상 열기"** 를 체크하면 다음부터 안 묻는다.
2. **시작** → 슬롯 1~6 을 훑어 키보드와 마우스를 찾고 채널 대응표를 보여준다.
   마우스가 자고 있으면 못 찾을 수 있다. 한 번 움직여 깨우고 **다시 검색**.
3. 상태창의 `키보드 채널N -> 마우스 채널M` 이 의도와 맞는지 확인한다.
4. 이후로는 알림만 남기고 계속 감시한다.

**첫 실행에서는 반드시 `시험 모드` 를 켜고 한 번 눌러보기를 권한다.**
전송 없이 어떤 판단을 내리는지 로그로만 보여준다.

### 버튼

| 버튼 | 하는 일 |
|---|---|
| 시작 / 정지 | 감시 서비스 |
| 다시 검색 | 슬롯 재탐색. 마우스를 깨운 뒤에 |
| 지금 맞추기 | 키보드가 있는 채널로 마우스를 보낸다 |
| 마우스→1/2/3 | 수동 전환 |
| 진단 | 인터페이스와 엔드포인트 구조를 적는다. **점유하지 않으므로 입력에 영향 없음** |
| 로그 복사 | 클립보드로 |

앱 아이콘 롱프레스(덱스 작업표시줄에서도)로 **지금 맞추기 / 마우스→1,2,3** 을
바로 실행할 수 있다. 화면 없는 `QuickActivity` 가 받아서 서비스에 넘긴다.

## 구조

```
Hidpp.kt         상수, 패킷 조립
UsbTransport.kt  인터페이스/쓰기방식 탐색, 리포트 입출력
Session.kt       요청-응답, 슬롯 탐색, 호스트 정보
FollowEngine.kt  이벤트 루프와 추종 판단
FollowService.kt 포그라운드 서비스
MainActivity.kt  화면
QuickActivity.kt 바로가기 진입점
```

### 하드코딩하지 않은 것들

맥에서 관측한 값이 안드로이드에서도 같다는 보장이 없어서 전부 실행 시에 찾는다.

- **HID++ 인터페이스 번호** — HID 인터페이스마다 리시버에게 실제로 말을 걸어보고
  대답하는 쪽을 쓴다. IN 엔드포인트가 20바이트 이상인 것부터 시도한다
  (부팅 키보드는 8바이트라 뒤로 밀린다).
- **쓰기 방식** — 인터럽트 OUT, 컨트롤 SET_REPORT(리포트 ID 포함/제외) 순으로
  시도한다. 볼트 리시버에는 OUT 엔드포인트가 없어서 컨트롤로 갈 확률이 높지만
  단정하지 않는다.
- **슬롯 번호** — 1~6 을 ping 하고 `DeviceNameAndType`(0x0005) func 2 의 종류
  코드로 키보드(0)/마우스(3)를 가린다.
- **feature index** — 매번 IRoot 의 `getFeature` 로 조회한다.

### 왜 이벤트가 유실되지 않는가

`Session.transact` 는 조회 응답을 기다리는 동안 도착한 이벤트/알림을 버리지 않고
`pending` 에 쌓아두고, 이벤트 루프가 그걸 먼저 꺼내 쓴다. 채널 전환 이벤트가
다른 조회와 겹쳐 사라지면 앱이 통째로 쓸모없어진다.

전환 전송은 계산 직후에 하고 로그는 그다음에 남긴다. 키보드가 떠나면서
링크 정리가 시작되므로 늑장 부릴 여유가 없다.

## 아직 검증 안 된 것

**실기기에서 한 번도 돌려보지 않았다. USB 허브가 없어서다.** 컴파일과 패키징만
확인했다. 허브가 오면 아래 순서로 확인할 것.

1. **진단** 버튼부터. 인터페이스 목록이 나오는지, 마우스 입력이 살아 있는지.
   여기서는 점유를 안 하므로 죽으면 안 된다.
2. **시작**. `HID++ 연결: 인터페이스 N, ...` 이 뜨는지, 어떤 쓰기 방식이
   채택됐는지 로그를 본다.
3. **그 직후 마우스를 움직여 본다.** 벤더 인터페이스를 강제 점유했을 때
   마우스 입력이 죽는지가 이 프로젝트 최대의 미검증 위험이다.
   죽는다면 접근을 다시 설계해야 한다.
4. 슬롯 탐색 결과와 채널 대응표가 맥에서 본 것과 같은지 대조.
5. **시험 모드로** 키보드 F1 을 눌러 판단이 맞는지 로그로 확인.
6. 시험 모드를 끄고 실제 전환.

### 그 외 미확인

- `0x1815` func 3 이후 (setter 위험 때문에 안 건드림)
- `0x1815` func 1 응답 offset 2 의 의미
- 컨트롤 SET_REPORT 에 리포트 ID 를 포함해야 하는지 — 양쪽 다 시도하게 짜뒀다
